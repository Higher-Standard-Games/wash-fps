# v0.9.25 QA: Code Improvement Candidates

Ten improvements found while reading the FPS code (client, server and simulation), each with a first-pass design. This is a **discussion document**: nothing here is implemented yet.

## How this was produced

- **Method:** reading source and `grep`. No profiler, no running game.
- **Tests:** the original analysis was read-only. Since then a way to run the game's tests, type-check and lint in a cloud session has been found (see "Running the tests" below), and item 3 has been implemented and tested with it. - **Engine repo:** some fixes touch `Higher-Standard-Games/shag` (read-only in this session). Those are flagged **[engine]**.
- **Gain is a judgement,** not a measurement. Items 2, 7 and 8 are optimizations and need a profile before any work starts.

## Running the tests

Verified in a cloud session on 2026-10-06. The engine repo is needed (this repo is a submodule and imports `../../../engine/...` by relative path).

1. Clone the engine (`Higher-Standard-Games/shag`) and run `npm install --ignore-scripts` in it (about 30 seconds).
2. **Copy** this repo into the engine at `src/games/fps/` (not a symlink: a symlink resolves to the real path and breaks the relative imports). For example: `tar -C <this-repo> --exclude=.git --exclude=docs -cf - . | tar -C <engine>/src/games/fps -xf -`. Re-copy after each edit.
3. From the engine: `npx vitest run src/games/fps/<path>` for tests, `npx tsc --noEmit -p tsconfig.json` for types (about 20 seconds), and `npx biome check <files>` for lint.

Result of the first full run: all 48 client test files (255 tests) pass, `tsc` is clean, and biome is clean on the touched files.

## First server measurements

Taken 2026-10-07 with `bench/` (3 runs each, median reported; Intel Xeon 2.10 GHz, 4 cores, Node 22.22). The spread between runs was under 5% for every scenario. Fixtures: 16 players, 20 projectiles, 10 dropped weapons, 8 damage events. A real server has a collision world, a gametype and PVS culling, which this leaves out, so read each number as a lower bound on its own part.

| Scenario | Median | p95 | p99 | Per second on a 16-player server | Verdict |
|----------|-------:|----:|----:|---------------------------------:|---------|
| `snapshot.build` | 30 µs | 43 | 53 | 1.9 ms (62.5 builds) = **0.2% of a core** | negligible |
| `snapshot.encode` (one full snapshot) | 251 µs | 281 | 286 | | |
| `snapshot.buildAndEncode` | 204 µs | 228 | 230 | | |
| **`snapshot.encodeClients16`** | **2,412 µs** | 2,807 | 2,898 | **151 ms = about 15% of a core** | **the hot spot** |
| `pickups.update` | 3.5 µs | 6.2 | 8.9 | 0.44 ms (125 ticks) = 0.04% | negligible |
| `hitscan.resolve16` | 1.0 µs | 7.0 | 10.8 | | negligible |
| `sim.tick16` (before the `[PHYS]` gate) | 51 µs | 98 | 277 | 6.4 ms = 0.6% | |
| `sim.tick16` (after) | **34 µs** | 69 | 114 | 4.3 ms = 0.4% | |

What this says:

1. **Encoding is the cost, and it scales with the player count.** Building a snapshot is 30 µs and happens once; encoding costs about 150 µs per client, because the broadcaster encodes separately for each client (`SnapshotBroadcaster.ts:100`). At 16 clients that is 2.4 ms per snapshot, 80 times the build, and 14 Mbit/s of output (1.8 KB per client per snapshot). At 62.5 snapshots a second it is about 15% of one core before PVS culling, and the tick loop shares that core.
2. **Item 8 as written (allocation in the builder) is not worth doing:** the whole build is 0.2% of a core. The target is the encoding. Item 8 is re-scoped below.
3. **Item 7 (pickup scans) is closed:** 3.5 µs.
4. **The simulation itself is cheap** (34 µs a tick for 16 players, 0.4% of a core). Without a collision world, though. A real tick costs more, and that is the number worth measuring next with map data.
5. **Per-tick work is not where the server's time goes; per-snapshot per-client work is.** Any server-performance effort should start there.

## Item 5: Hit location

### Finding

The head and legs classification is copy-pasted in two places:

- `WeaponSystem.ts:1277–1279` (melee)
- `WeaponSystem.ts:1669–1671` (hitscan)

```ts
const yOffset = closestPoint.y - target.y;
if (yOffset > 32) hitLocation = Head;
else if (yOffset < -20) hitLocation = Legs;
```

### Probable bug

For hitscan, `closestPoint` is the point on the ray **closest to the target's centre**, and a hit requires that point to be within `hitRadius = 32` of the centre (`distSq >= 32² → continue`). So `|yOffset| < 32` always, and `yOffset > 32` can never be true. **Head hits cannot register for hitscan weapons** (Machinegun, Riotgun, Electrobolt, Instagun, Voltaic), and the ×2 head multiplier is dead for them. Legs (`< -20`) still can. For melee the test is wider (`hitRadius + 32`), so a head hit is possible there.

Supporting evidence: the only hitscan accuracy test asserts `headshots` is 0 for "a body hit along the level ray" (`WeaponSystem.test.ts:721`), and nothing asserts a positive headshot. **This needs a unit test to confirm before we change anything.**

### Decision

Head hits should give a damage bonus on hitscan weapons, from the **upper part of the player's body**. This section is the design for that.

### Hit volume

- The player hull is **16 radius, 64 tall**, from 24 below the origin to 40 above it (`PlayerPhysicsConstants.ts`: `PLAYER_RADIUS`, `PLAYER_MINS_Z`, `PLAYER_MAXS_Z`).
- Hitscan currently tests a **sphere of radius 32 around the origin**, twice the hull's radius and not tall enough to reach the head. So shots near the body edge hit that visibly miss, and the head is cut off.
- **Proposal:** test a vertical cylinder instead, with its own named constants (`HIT_RADIUS`, `HIT_MIN_Z`, `HIT_MAX_Z`), and classify by the height at which the ray **enters** it.
  - **Head:** the top quarter, 24 to 40 above the origin (16 units).
  - **Legs:** the bottom quarter, 24 to 8 below the origin. Today "legs" is only the last 4 units above the feet, so it almost never triggers.
  - **Body:** everything between.
- **Keep the feel in mind:** the radius-32 sphere is generous, and a true 16-radius hull will feel harder to hit. Start `HIT_RADIUS` at 20 and tune from there; it is one constant.
- Rewound (lag-compensated) positions use the same test.

### Outcome (implemented)

The design below was settled in discussion into something simpler, and this section records what shipped.

- **Rule:** a head hit does **+10%** damage, a leg hit keeps **−25%**. One flat multiplier for every weapon (`HEAD_DAMAGE_MULTIPLIER`), so none of the per-weapon concerns below apply.
- **The bug was real.** Head hits could never register for hitscan weapons: the head threshold was 32 above the target's origin, and the closest ray point to a sphere of radius 32 cannot be more than 32 away. The fix puts the thresholds at **+20 / −20** (`HEAD_MIN_OFFSET`, `LEGS_MAX_OFFSET`) and moves the classification into one function, `classifyHitLocation`, used by both the melee and the hitscan paths. The head tests fail if the threshold goes back to 32.
- **Hit volume left alone.** The sphere test is unchanged, so hit feel does not change. The cylinder hull in the design is still an option, but it is a separate decision with its own balance impact.
- **No headshots for the Riotgun** (decided afterwards): its pellets are a distributed blast, not an aimed shot. A pellet at head height counts as a body hit (`locateHit`, which uses the same pellet test as `fireHitscan`); leg hits still count. Treating pellets as always-body, legs included, would be a one-line change to `locateHit` if wanted.
- **Merged damage.** A shotgun's pellets arrive as one number; the number reports the most specific location among them (head over legs over body). With the rule above, for the Riotgun that means legs or body.
- **Feedback:** a head hit shows an **orange** damage number and a **300 ms** crosshair flash (200 ms otherwise). The client reads `hitLocation` when present and treats an event without it as a body hit.
- **Wire:** a head or leg hit travels as a new `damage` event code, **23**, with one extra byte. A body hit keeps code 10 and its exact bytes, so old demos decode unchanged (pinned by a test against the old encoder's output). This is the engine patch in `patches/engine-damage-hit-location.patch`; see `patches/README.md`.
- **Tests in this repo:** `HitLocation.test.ts` (17), `SnapshotDamageEvent.test.ts` (4), `HitFeedback.test.ts` (6), `OutgoingDamage.test.ts` (7). The whole FPS suite passes (131 files, 1,024 tests) and `tsc` is clean.

**To finish:** merge the engine branch `claude/inspiring-fermi-1fv0ga`, which carries the patch. Until then head hits do the extra damage, but the orange number and longer flash do not appear, because the old encoder drops the field.

**Remaining question:** the telemetry log line at `GameServer.ts:817` reports each player's headshot percentage. It was always 0% before; it now reports real values, so any anti-cheat threshold built on it needs calibrating against real play, not against the old zeros.

### Per-weapon multiplier (superseded: kept for the record)

A single global ×2 is too blunt, because the weapons fire very differently. Add an optional `headMultiplier` to `WeaponDef` (default 1.0) and use it in place of the global head entry in `LOCATION_MULTIPLIER`.

| Weapon | Damage | Head ×2 | Head ×1.5 | Proposal | Why |
|--------|-------:|--------:|----------:|---------:|-----|
| Electrobolt | 75 | 150 | 113 | **1.5** | 113 kills an unarmored full-health player, and armor still matters |
| Machinegun | 10 | 20 | 15 | **1.5** | Rewards aim at 10 shots/s without doubling its damage per second |
| Instagun | 200 | | | not needed | Already kills in one hit |
| Riotgun | 5 × 18 pellets | 10 per pellet | 8 per pellet | **1.0** to start | With the 8° spread, a lucky cluster on the head would swing a shot from 90 to well over 100 |
| Voltaic | 7 per tick, 20/s | 280 per second | 220 per second | **1.0** | A continuous beam: head tracking would double its already high 140 damage per second |
| Blade | 80 | 160 | 120 | **1.0** | Melee hits resolve on a cone, so a head hit is not a deliberate act |
| Rocket, grenade, plasma | | | | **n/a** | Projectile direct hits and splash are body hits |

These numbers are a starting point for a balance discussion, not a final answer. They change what "a good shot" is worth, so play-test with bots and people.

### Feedback

The `damage` event on the wire (`SnapshotEvent.ts:144`) carries only the victim, attacker, amount, weapon and position, **not the hit location**, so the client cannot tell a headshot from a body shot. A headshot that plays no distinct sound and shows no distinct number feels like it did not happen.

- **Option 1 (recommended):** add a `hitLocation` byte to the `damage` event. It is a wire and demo format change **[engine]** (`BinaryProtocol` encode and decode, and a demo version bump), so it ships together with the rule change.
- **Option 2:** leave the protocol alone and ship the rule without feedback first. Players get the bonus but no cue.

With it, the client can colour the damage number, play a distinct hit sound, and flash the crosshair differently.

### Steps

1. A unit test that **proves the bug first**: a hitscan ray aimed at head height records `Body` (or misses the head) today.
2. Extract `classifyHitLocation(entryY, originY)` with the named constants, and use it in both the melee and hitscan paths.
3. Replace the sphere with the cylinder, using the rewound position when lag compensation applies.
4. Add `headMultiplier` to `WeaponDef` and the weapon definitions **[engine]**.
5. Tests: head, body and legs for each hitscan weapon; a lag-compensated shot; a crouched target (the hull's minimum rises to −4, `CROUCH_MINS_Z`, so the quarters must scale with the current hull).
6. Update the player manual's combat page and remove its "Under review" note.

### Risks

- It changes combat balance, so the table above needs a play-test and probably a second pass.
- Bots' fire planning and the `headshots` accuracy telemetry (`WeaponSystem.ts:1419`, used for anti-cheat) change meaning with it, and the anti-cheat calibration (`anticheat-calibrate`) should be re-run.
- A cylinder test costs a little more than a sphere test, which is negligible at 16 players.

## Item 10: Oversized files, `any` in event helpers, log noise

### Finding

- `Game.ts` is 2,864 lines; `initializeNetwork` alone is **413 lines**. `GameEvents.ts` is 1,285 lines with 23 `any`, and there are 64 `any` across the game code.
- **Events are already typed on the client dispatch path** (see the correction above): `SnapshotEvent` is a discriminated union of 20 event types in the engine, and the `switch` at `GameEvents.ts:234` is exhaustive. The remaining `any` is in the helpers it calls, for example `handleAwardEvent(ctx, event: any)` and `HUDState.processDamage(event: any)`, which each have a matching member of the union they could take.
- The server side is the unchecked half: `SnapshotBuilder.ts` pushes object literals into `GameState.events`, whose element type is a loose bag (`[key: string]: any`, `GameState.ts:8`). Misspelling a field there compiles and fails silently on the client.
- `GameServer.ts` has 55 `console.log` calls and `GametypeController.ts` 23.

### Where the event types should live

**They already live in the engine, and that is the right place.** `SnapshotEvent.ts` says it mirrors `BinaryProtocol`'s per-type encode and decode schema, so the codec, the demo tools (`DemoAnalyzer` reads events by type string) and this game all share one definition. The union does carry game-specific events (`weapon_fire`, `voltaic_beam`), which is a small blur of the engine/game line, but moving it out would split the codec from its schema. Keep it where it is.

### Design

1. **Type the server's pushes.** Add a small `emit(events, event: SnapshotEvent)` helper (or type the `events` array as `SnapshotEvent[]` for the builder's local use) so every push in `SnapshotBuilder.ts` is field-checked against the same union the client uses. This is a type-only change at first.
2. **Narrow the helpers.** Change `event: any` in the `GameEvents.ts` helpers and `HUDState.process*` to the specific member (`AwardSnapshotEvent`, `DamageEvent`, ...).
3. **Split `Game.ts` by lifecycle, not by size.** Candidates: network join and teardown (`initializeNetwork`, `joinGame`, `shutdown`), input and spectator key handling (the five `document` listeners at `Game.ts:1194–1242`), and per-frame rendering (`renderRemotePlayers`). Each becomes a class owned by `Game`, keeping `Game.getInstance()` as the facade so callers don't change.
4. **The logger that already exists does not filter, so adopting it alone changes nothing at run time.** `engine/core/Log.ts` is a tag wrapper: `log.debug` and `log.info` call `console.log`, and production **client** builds strip `console.log`/`console.debug`. The server runs under `vite-node` and is not stripped, so `log.debug("X", ...)` still prints there. (An earlier version of this document said the logger would quiet the server console; that was wrong.) To get a quiet server, the logger needs a **run-time level** (for example `SHAG_LOG_LEVEL`, default `info`, making `log.debug` a no-op) **[engine]**, and then the noisy calls move to `log.debug`. For the one worst case, the always-on `[PHYS]` diagnostic, this has been done differently and already: it is opt-in with `SHAG_DEBUG=phys`. The rest of the per-tick, per-hit and per-message output was handled the same way (see the log-noise outcome under item 10).

### Risks

### Outcome of the log noise (step 2)

Every server `console.log` was classified. Lifecycle messages (a player joins, a match starts, a demo is saved, the 5-second tick-rate and telemetry lines) stay. What fired per tick, per hit or per message is now either deleted or opt-in through one variable, `SHAG_DEBUG` (`server/DebugLog.ts`, four tests):

| Was | Now |
|-----|-----|
| `Cached N kill events…` on every kill; `acked tick` every 1,000 ticks per client; message distribution every 500 messages; the floor trace on every join | Deleted (they were development scaffolding) |
| `[PHYS]` per player per second | `SHAG_DEBUG=phys` |
| `[KB]` and `[KB POST-SIM]` on every knockback | `SHAG_DEBUG=kb` |
| `[FallDamage]` on every landing, even safe ones | `SHAG_DEBUG=falldamage` |
| button sample every 200 inputs | `SHAG_DEBUG=input` |
| `[Perf] snapshot encode` every 100 ticks | `SHAG_DEBUG=perf` |
| `[Discharge]` | `SHAG_DEBUG=discharge` |

The messages are built lazily, so a topic that is off costs nothing. A real log level for the engine's `log.debug` still needs the engine change described above.

Steps 1 and 2 are cheap and safe, and a good first slice. Step 3 is the large one: do it piecemeal, one extracted class per commit, with the item 9 tests in place first.

## Item 3: Event listeners never removed

### Finding

There are 111 `addEventListener` calls against 19 `removeEventListener` in the client. Two on `document` are never removed:

- `Crosshair.ts:87`: an anonymous `pointerlockchange` listener added on **every** `init()`, which `Game.ts:1106` calls on each match joined. `destroy()` removes the DOM but not the listener.
- `FPSHud.ts:289`: `_pointerLockHandler` is stored but no matching `removeEventListener` exists in `FPSHud`.

(The `visibilitychange` listener at `Game.ts:650` is in a singleton constructor and runs once, so it is not a leak.)

### Design

Use one `AbortController` per owner:

```ts
this.abort = new AbortController();
document.addEventListener("pointerlockchange", handler, { signal: this.abort.signal });
// destroy():
this.abort.abort();
```

This also fixes the rest of the pattern. The `Game.ts` key handlers (`_specCycleKeyHandler`, `_joinKeyHandler`, ... and their five matching removals at `Game.ts:2494–2510`) could share one controller instead of five hand-matched pairs, so a future listener can't be added without a way out.

### Risks

Low. Check that `destroy()` and `init()` are called in matching pairs (the `Crosshair` singleton is re-`init`ed, so `init()` should abort any previous controller first).

## Item 6: Per-tick position cache; maps that only grow

### Finding

Every tick, `GameServer.tick()` (`GameServer.ts:828–833`) loops over **all** entities (players, projectiles, items) and stores each owned entity's position in `WeaponSystem.entityPositions`. That cache is read in only two places, both about dropping weapons (`WeaponSystem.ts:643` for a pickup swap and `:720` for a death). It is never pruned except by `reset()` (`:301`), so it holds an entry for every player and bot that ever joined. `knownProjectileIds` (`GameServer.ts:92`) likewise grows with every projectile until the next match start. Entity ids are monotonic (`WorldState.nextEntityId++`), so this is memory growth, not a correctness bug.

### Design

- **Death drops:** `KillEvent` already carries `victimX/Y/Z` (`CombatSystem.ts:92–95`), so `dropAllWeapons` can take the position from the kill event and the per-tick cache is not needed for that path.
- **Pickup swap:** pass the player's current `transform.position` into the swap call from the system that already holds the entity.
- Delete `cacheEntityPosition` and the loop in `tick()`.
- For `knownProjectileIds`, delete an id when its projectile is removed (the projectile system already knows), or replace the set with a "spawn sent" flag on the projectile entry.

### Risks

Low, but **watch determinism**: the drop toss is seeded from tick and entity id (`rngFrom(this.currentTick, entityId, 1)`) so demo re-simulation reproduces it. The cache holds the **pre-tick** position; the kill event holds the **post-tick** one. The drop would land up to one tick of movement away, which is still deterministic, but `ReSim` and `KnockbackReplay` tests should be run to confirm the demos still verify.

## Item 1: Hardcoded 125 Hz literals

### Finding

`ServerTiming.ts` was written so that "everything time-based derives from one immutable value", yet literals remain: `GametypeController.ts:169,589,590`, `WeaponSystem.ts:40,932,950,951,1010`, `PickupSystem.ts:42`, `SearchAndDestroy.ts:135`, `DroppedWeaponSystem.ts:75`. The server accepts `--tickrate`, but the engine also hardcodes 125 (see the corrections above), so a non-125 rate would not be correct today even if these were fixed.

### Design

**Decided: 125 Hz is fixed (option A).** The text below keeps both options for the record.

- **Option A (chosen): declare 125 Hz fixed.** Import one `TICK_RATE` (the engine already has `DEFAULT_PHYSICS_TICK_RATE`) in all eight places, and make `createServerTiming` and `--tickrate` reject anything else, or at least warn loudly. Smallest change, makes the existing assumption explicit.
- **Option B: make the tick rate truly configurable.** Pass the `ServerTiming` into each system's constructor and use `secondsToTicks`. This is much larger, because it also needs the engine's constants (`BombModel`, `lagcomp`, `ItemThrow`, `TickConfig`) and the shared simulation to follow.

### Risks

Option A is low risk. Option B needs an engine-wide pass and a test at a second tick rate. Either way, add a test that fails if a new `* 125` literal appears (a simple grep-style lint test).

## Item 2: HUD change detection

### Outcome (implemented, and not what was designed)

The design below was written from reading the code. Before building it I timed every HUD widget's `update` in jsdom against an unchanged state (16 scoreboard rows, three weapons, a warmup match). **The premise was wrong.** The numbers, per 50 ms poll:

| Widget | Cost | Note |
|--------|-----:|------|
| `PhaseMessage` | 98–147 µs | rewrote `innerHTML` every poll during warmup |
| `ReadyBar` | 65–72 µs | the same, in warmup or while spectating |
| `Scoreboard.refresh` (open, unchanged) | 4–5 µs | the `JSON.stringify` signature I suspected |
| `HUDState.updateScoreboard` (per snapshot) | 5 µs | rebuild and sort of 16 players |
| `VitalsBlock` | 1.4 µs | |
| `WeaponRack` | 0.5–0.6 µs | the other `JSON.stringify` suspect |
| everything else (13 widgets) | 0.03–0.26 µs each | |
| **Total** | **about 180 µs** | **0.36% of the interval** |

So change detection by `JSON.stringify` was never the cost, and the revision-counter design would have saved a few microseconds. What the measurement did find is two widgets that throw their elements away and rebuild them on every poll. That is also a visible bug: the warmup title has a 0.18 s stamp animation (`w-board-stamp`), and rewriting it every 50 ms restarts the animation before it can finish, so the title never settles during the whole warmup (up to two minutes).

**What shipped:** `PhaseMessage` and `ReadyBar` write only when their output changed (`showHtmlIfChanged`, and a keyed `write`). A phase change still forces a rewrite, because replaying the animation is the point there. The ready bar still re-applies its classes on every poll, which is free when they hold and keeps it visible if `show()`/`hide()` was called from outside. After: `PhaseMessage` 2.6 µs, `ReadyBar` 8.6 µs.

**Caveats:** jsdom is not a browser, so the absolute numbers mean little; they show where the work is, not how long it takes in Chrome. In a real browser the rewrite also costs layout, and the restarting animation is a visible effect, so the benefit is probably larger than the table. I have not watched it in a browser.

### Original finding and design (superseded by the outcome above)


`FPSHud` runs one `setInterval` at 50 ms (`FPSHud.ts:509`) that calls `update()` on every widget. Two widgets decide "did anything change?" by building strings:

- `WeaponRack.update` (`WeaponRack.ts:80`) builds `${active}|${owned.join(",")}|${JSON.stringify(ammoMap)}` 20 times a second.
- `Scoreboard.refresh` (`Scoreboard.ts:155–199`), while open, copies and spreads the entries and calls `JSON.stringify` on teams, scores and rows every tick.

`HUDState.updateScoreboard` also rebuilds and re-sorts the whole array on every snapshot (about 62 Hz), so the entry objects are never identical between calls and identity checks can't be used downstream.

### Design

`HUDState` is only changed through a few `process*` methods, which makes a revision counter cheap:

1. Add `revision` counters per slice: `weaponRevision`, `scoreboardRevision`, `vitalsRevision`.
2. In `processWeaponState` and `updateScoreboard`, compare the new data to the old **once** (a shallow loop, not a string) and bump the revision only on a real change.
3. Widgets keep `lastRevision` and early-return when it hasn't moved. The signature stays as a debugging aid if wanted.
4. Time-driven widgets (timer, countdown, expiring damage numbers) keep polling; they don't use the counters.

An alternative is to push instead of poll (`HUDState` emits a change event per slice), but that touches every widget; the counter approach changes two and can spread later.

### Risks

Medium: a missed `revision++` freezes a widget. A test per slice that asserts "revision bumps on change, not on identical input" covers it. **Measure first**: 20 string builds a second is probably invisible next to the renderer, and a profile may say this is not worth the change.

## Item 8: Snapshot allocation

### Re-scoped by the first measurements

The design below targets the allocation in `buildSnapshot`. Measured, that is 30 µs a snapshot, about 0.2% of a core, and is **not worth doing**. The cost is in encoding the snapshot once per client: about 150 µs per client, 2.4 ms for 16 clients, roughly 15% of a core (see "First server measurements"). The work for this item is therefore:

1. **Find out where the 150 µs goes.** Profile `snapshot.encodeClients16` (`node --cpu-prof` through `vite-node`) and split it into the entity components, the events, the strings (entity ids and weapon ids are sent as strings), the delta computation against the baseline, and buffer growth. This is cheap and decides everything below.
2. **Likely candidates, to confirm with the profile:**
   - **Encode the shared part once.** Events and player state are the same for every client apart from PVS filtering and the client's own entity, so the event section could be encoded once and copied.
   - **Per-client buffer reuse** (a pooled `BinaryEncoder`) instead of allocating a growing buffer each time.
   - **Cheaper strings:** ids like `player_7` and weapon names are written as length-prefixed strings in every event, every snapshot. A small table of ids per match, sent once, would shrink events and the work.
   - **Cheaper delta:** only diff entities that changed since the baseline.
3. **Keep the wire format and demos intact**, and keep the `f32` rounding exactly (the comment at the top of `SnapshotBuilder.ts` explains the reconciliation drift it prevents). Any change goes through the byte-level golden test pattern used in `DamageHitLocation.test.ts`.
4. **Measure with PVS on** before trusting a gain: culling gives each client fewer entities, so the real per-client cost is lower than this fixture.

The bytes matter as much as the time: 1.8 KB per client per snapshot at 62.5 Hz is 14 Mbit/s for 16 clients.

### Original design (superseded)

### Finding

`buildSnapshot` (`SnapshotBuilder.ts:127+`) creates a new `Entity` for **every** projectile and dropped weapon on every snapshot, each with `transform`, `position` and `velocity` components that repeat the same numbers (the position is stored in both `transform.position` and `position`, with `f32` applied three times), plus no-op `serialize`/`deserialize`/`clone` closures. Both components are read downstream (`InterpolationBuffer.ts:141` reads `position`; other code reads `transform`), so the duplication is not accidental.

### Design

Measure before changing anything: count allocations per snapshot with a loaded 16-player match (a Node heap profile, or `--trace-gc`). If it matters:

1. Hoist the per-component `serialize/deserialize/clone` closures to module-level singletons (already partly done: `_noopSerialize`).
2. Make the `position` component a **view** of the transform's position rather than a copy.
3. Reuse entity objects across snapshots with a pool keyed by entity id, reset on each build.
4. Keep `f32` quantization exactly as it is: the comment at `SnapshotBuilder.ts:48–55` explains it prevents a systematic reconciliation drift.

### Risks

High: the output is the wire format and the demo format. Do **not** start without the item 9 golden test, and verify demo recordings stay byte-identical.

### Outcome

`bench/profile.ts` runs any scenario under Node's sampling profiler (`npx vite-node src/games/fps/bench/profile.ts -- --scenario snapshot.encodeClients16`). For 16 clients, self time per snapshot was:

| Where | Before |
|-------|-------:|
| `TextEncoder.encode` and its native part (one new array per string) | 57% |
| `getData` (copy out via `ArrayBuffer.slice`) | 23% |
| Entity, event and player encoding together | about 12% |

So the cost was never the entities; it was allocating a byte array for every string (ids, names, weapon ids) and copying the result. Two changes in the engine's `BinaryEncoder`, **no change to a single output byte**:

1. `writeString` reserves the worst case (3 bytes per UTF-16 unit) and uses `TextEncoder.encodeInto` to write straight into the buffer, then fills in the length.
2. `getData` copies with `new Uint8Array(buffer, 0, offset).slice()`.

| Benchmark (4-core Xeon 2.1 GHz, Node 22) | Before | After |
|-----------|-------:|------:|
| `snapshot.encodeClients16` | 2,437 µs | 398 µs (6.1×) |
| `snapshot.encode` (one snapshot) | about 150 µs | 23.5 µs |
| bytes per client | 1,774 | 1,774 |

At 62.5 snapshots per second that is about 15% of a core down to about 2.5%. The engine test `shared/net/__tests__/Utf8Encoder.test.ts` pins the bytes against `TextEncoder` for empty, ASCII, accented, CJK, astral, lone-surrogate and 20,000-character strings; the existing 547 engine network and server tests, including the byte-exact snapshot and demo tests, pass unchanged.

**Correction (2026-10-07):** the faster `writeString` threw on a non-string value, which `TextEncoder.encode` had silently coerced, and `item_pickup` sends a numeric id. Found by item 10's typing and fixed on the engine branch before merge (`730e1f2`); the patch file here predates the fix.

Not done, and now probably not worth it: sharing the event section between clients, pooling buffers, an id string table. Re-profile first; the remaining time is spread thinly.

**Correction 2 (2026-10-07):** the fixture behind these numbers had no connected clients and no weapons, so its snapshots carried neither the per-player `weapon_state` nor the scoreboard standings. The new `snapshot.broadcast16` scenario includes both: **5,809 bytes per client** (not 1,774) and **1,347 µs per snapshot for 16 clients, about 8% of a core** (not 2.5%). The encoder fix still holds, but sharing the event section between clients is worth doing after all. See B3 in [v0.9.26-QA.md](./v0.9.26-QA.md).

## Item 4: Dynamic `import()` on the hit path

### Finding

On every damage event dealt by the local player, `GameEvents.ts:462` runs `import("../client/Crosshair")` and `:464` runs `import("../client/DamageNumbers")`. Both modules are already statically imported (`Game.ts:42`, `DemoService.ts:47`), so the dynamic form does not split anything off and only adds an async hop and a promise per hit. The same block reads a private field through `(dn as any)["scene"]`.

### Design

- Import `Crosshair` and `DamageNumbers` statically at the top of `GameEvents.ts` and call them directly.
- Give `DamageNumbers` a public `isInitialised()` instead of the `as any` poke.
- Check the other 55 dynamic imports in `client/` for the same pattern. Some are probably deliberate cycle breakers (`import("../Game")` appears five times), so each needs a look rather than a blanket rewrite.

### Result of checking the other 12 dynamic imports in `GameEvents.ts`

Only the two on the hit path were converted. The rest were each looked at and left, for these reasons:

| Import | Where it runs | Decision |
|--------|---------------|----------|
| `./FPSHud` (twice) | pickup toast, a chat or event line | **Keep.** `FPSHud` imports `Game`, which imports `GameEvents`: a static import is a cycle |
| `../client/DroppedWeaponRenderer` (twice) | weapon drop and pickup | **Keep.** Rare events, and a heavy module that pulls in the renderer |
| `engine/weapon/WeaponViewManager` (twice) | weapon state events | **Keep for now.** A very large engine module; a static import moves its load into start-up. Worth measuring, not guessing |
| `engine/ui/hud/DamageOverlay` | every hit the local player takes | **Candidate.** The same per-hit promise as the one removed. Not converted because I did not check that it is already loaded elsewhere, and a wrong guess changes start-up |
| `engine/ui/hud/EventFeed`, `AwardBanner` | an award or chat line | **Keep.** Rare |

The type-only reference (`import("./DeathCamera").DeathCamera`) at the context definition costs nothing at run time.

### Risks

Low. A static import can create a circular dependency that the dynamic one avoided, so each import was checked for a cycle first (the two converted ones import only `Cvar` and Babylon).

`pickups.update` with 16 players and 60 pickups costs **3.5 µs per tick**, which is 0.44 ms per second, or 0.04% of a core. Nothing below is needed. The original analysis follows for the record.

## Benchmark and profiling plan

> The full design now lives in [performance-and-demos.md](./performance-and-demos.md): what already exists, how recorded demos and the re-sim oracle can serve as deterministic workloads, the metrics and hook points, the result format and a step-by-step implementation plan. The summary below is kept for context.

Items 2, 7 and 8 are optimizations. We should not touch them without numbers, and every other item benefits from a regression check. The aim is a few **standard scenarios** that anyone can run and that print comparable numbers, so a change can be judged by a before/after diff.

### What already exists

All in the engine repo's `src/cli/`:

| Tool | What it gives us |
|------|------------------|
| `demo:record` (`record-demo.ts`) | Boots a **real `GameServer`** headlessly on a real map, adds N bots, and runs for S seconds. This is exactly the shape of a server benchmark |
| `server:fuzz` | A seeded, deterministic simulation run with random inputs; catches NaN and non-determinism |
| `net:viewlag` (`measure-viewlag.ts`) | Measures how stale the world a client aims at is, over a real socket with held latency |
| `bot:bench` | Cost of the neural bot overlay per decision |
| Server diagnostics | `GameServer.logTickRateDiagnostic` already logs actual tick rate and `maxTickWork` every 5 seconds, and `Telemetry` logs per-client jitter and loss |

What is missing: a **machine-readable result** (the diagnostics are log lines), **percentiles** instead of one max, **snapshot size and GC** numbers, a **client-side measurement**, and **fixed scenarios** with saved baselines.

### Three layers

**Layer A: server macro benchmark** (needs map data)

A `bench:server` script, built on the `demo:record` approach, with a fixed set of scenarios:

| Scenario | Map / mode | Players | Why |
|----------|------------|--------:|-----|
| `duel` | `wdm2`, Duel | 2 bots | The lightest realistic match; a floor |
| `ffa8` | `wdm7`, Deathmatch | 8 bots | The lobby's FFA room size |
| `ffa16` | `wdm7`, Deathmatch | 16 bots | A full dedicated server; the stress case |
| `snd10` | `wbomb2`, S&D | 10 bots | Objective mode, rounds, bomb events |

Each runs for 60 seconds after a 10-second warm-up, with bots at a fixed difficulty. It records, per scenario:

- **Tick work** (p50, p95, p99, max in ms) by timing the body of `GameServer.tick()`, which has a natural place for an optional timing hook.
- **Snapshot build time and byte size** (per snapshot, and per client after PVS).
- **GC:** count and total pause from `perf_hooks` (`PerformanceObserver` on `gc` entries), run with `--expose-gc` so a full collection can be forced between scenarios.
- **Heap:** start, end and peak `process.memoryUsage()`, which is also how we would catch item 6's growth.
- **Outcome sanity:** ticks actually run vs. expected, so a too-slow run is reported and not silently averaged.

Output is one JSON file per run, plus a small script that diffs two runs and prints the percent change per metric. Bots are not deterministic between runs, so we compare **medians of 5 runs** and treat changes under about 10% as noise.

**Layer B: micro benchmarks** (no map data needed)

Small `vitest bench` files that build a fixed fixture and time one function:

| Benchmark | Item |
|-----------|------|
| `buildSnapshot` with 16 players, 20 projectiles, 10 dropped weapons | 8 |
| `PickupSystem.update` with 16 players and 60 pickups | 7 |
| `HUDState.updateScoreboard` plus one pass of every HUD widget (jsdom) | 2 |
| `WeaponSystem` hitscan resolution with 16 targets | 5 |
| The per-tick position-cache loop vs. none | 6 |

These run in seconds, need no assets, and are the right tool for proving or killing items 2, 7 and 8 before any design work.

**Layer C: client benchmark** (needs map data and a browser)

A Playwright script (Chromium is installed in the environment) that opens the game against a Layer A server and records, for 60 seconds:

- frame time distribution (`requestAnimationFrame` deltas) and long tasks (`PerformanceObserver` with `longtask`);
- JS heap and listener count (to confirm item 3: it should stay flat across match changes);
- time spent in `FPSHud.update`, via `performance.measure` around it.

Caveat: headless Chromium renders with a **software GPU**, so absolute frame rates mean nothing. Only the JavaScript-side numbers are comparable, and only against other runs on the same machine.

### Reproducibility rules

- Run on an otherwise idle machine, ideally pinned to one core (`taskset`), and record the Node version, CPU model and commit in the result file.
- Warm up first (the JIT needs it), then measure; repeat five times and report the median.
- Keep the baseline results in the repo (for example `bench/baselines/<machine>.json`) so a later change has something to compare against.
- Report the **baseline before any optimization commit**, and the after-numbers in that commit's message.

### Practical constraints

- **Map data.** Layers A and C need the game's map files, which are not in either repo (`public/data/` is gitignored and absent in this session). Layer B and the synthetic fuzz run do not.
- **Where the code lives.** The scenario definitions fit in this repo (`bench/`), but they run through the engine's `vite-node`, as the other CLIs do. The engine repo is read-only for me in this session, so anything that needs a new engine CLI (a `bench:server` entry in `package.json`) must be added there by you or after a permission change. A script in `bench/` that is run directly with `npx vite-node` works without touching the engine.
- **Running tests here.** This session could probably run the FPS tests by linking this repo into a clone of the engine (`src/games/fps`) and installing its dependencies. I have not tried it. It would let me confirm items 5 and 9's tests actually pass before pushing.

### Suggested first slice

1. Layer B benchmarks for items 2, 7 and 8, to decide whether they are worth doing at all.
2. The hit-location test from item 5, which doubles as the first regression test.
3. Layer A with the `duel` and `ffa8` scenarios, once map data is available to run it against.
