## Summary

Stop resending two things nobody's view has changed: the scoreboard roster inside `match_state`, and other
players' `weapon_state`. That should take a 16-player snapshot from 5,809 bytes to roughly 2 KB per client
when players are idle and 3–4 KB in a firefight, where every shot changes a player's ammo. A benchmark with
firing has to confirm it. The work stays in the game's server and client code, with no engine, binary layout
or demo format change.

Today each client gets 5,809 bytes per snapshot at 62.5 snapshots a second: about 2.9 Mbit/s per player and
46 Mbit/s out of a 16-player server. Measured with the `snapshot.broadcast16` benchmark.

| Part of one client's snapshot | Bytes | Changes |
| --- | ---: | --- |
| `weapon_state`, 16 × about 168 bytes | 2,695 | When a player fires, reloads, switches or picks up |
| `match_state` roster (`standings` + `spectators`) | 1,185 | On a kill, a join, a leave or a rename |
| Rest of `match_state` (phase, timer, scores) | 325 | Every tick: the timer is a float |
| Entities, `combat_state`, players | 1,341 | Already delta-compressed or small |

The rule that keeps it safe: a value is left out only once the client has acknowledged a snapshot that
carried it. Until then it is sent every time, exactly as now. As a safety net, every 125th snapshot (about
every 2 seconds) carries all of it anyway. The entity full snapshot every 64th is not touched.

## How snapshots work today

Entities and players are already delta-compressed against the snapshot the client acknowledged. Events are
not: every event is written in full in every snapshot. Read from the code on the work branch:

1. **Build, once per snapshot.** `buildSnapshot` (`server/SnapshotBuilder.ts`) makes one shared `GameState`.
   It holds a `weapon_state` event for every player and one `match_state` event, with `standings` and
   `spectators` spread into it.
2. **Per client.** `SnapshotBroadcaster.broadcast` takes a shallow copy per client, filters
   `knockback_state` to the owner and adds that client's agent directives. It picks the baseline
   `sentSnapshots.get(lastAckedTick)`, and sends a full snapshot with no baseline every 64th time. It encodes
   with `MessageCodec.encodeSnapshot` and keeps only entities and players in history.
3. **The demo.** After the broadcast, `DemoRecorder.recordFrame` encodes the same shared `GameState` with no
   baseline. Demos therefore get every event in full, whatever the broadcaster does per client.
4. **The wire.** The server runs over WebSocket only, which is reliable and ordered. The code is written for
   loss anyway (datagram naming, ack-named baselines), so the plan must stay correct for WebTransport later.
5. **Client acceptance.** `SnapshotReceiver.receive` is shared by the browser, bots and headless clients. It
   drops any snapshot whose tick is not newer than the last accepted one, and drops one whose baseline is
   missing. Only an accepted snapshot is published and acknowledged (`NetworkGameHost.handleSnapshot` →
   `sendAck`, sent reliably).
6. **Client use.** `Game.onServerStateUpdate` runs `handleServerStateUpdate` synchronously for every
   accepted snapshot, but only after the ack has gone out: `NetworkGameHost.handleSnapshot` acks at line 813
   and runs the callbacks at 826. If any handler throws, the rest of that snapshot's events are skipped, the
   error is caught and logged, and the server still counts the snapshot as delivered. `match_state` goes to
   `MatchStateManager.processEvent`, which overwrites every field, with `standings ?? []`. Your own
   `weapon_state` drives inventory, reload, fire timing and the viewmodel (`handleWeaponStateSync`). Another
   player's only sets `enemyWeapons` (their third-person model and kill feed), and drives the HUD while you
   spectate them.
7. **Server ack.** `nextAckedTick` only moves `lastAckedTick` forward. A resumed seat clears `sentSnapshots`
   and sets `lastAckedTick` to 0.

What each consumer reads:

| Consumer | `match_state` | Other players' `weapon_state` |
| --- | --- | --- |
| Browser client | Every field; `standings` only when the scoreboard has no live rows (post-game) | `currentWeapon`; the full state while spectating that player |
| Bot (`BotGameState`) | `gametypeName`, `phase`, `teamRoles`, `roundState` | Not read; own state only |
| Demo playback (`DemoService`) | Reads its own recorded frames | Reads its own recorded frames |

Noticed on the way: WebSocket connections never set `latency`, so `standings` always carry ping 0. The
scoreboard's live ping comes from the player rows, so nothing visible depends on it.

## The design

A value can be left out of a client's snapshot only after that client has acknowledged a snapshot that
carried it. All of it happens per client in `SnapshotBroadcaster`, on that client's copy.

**What it applies to.** Each value has a key:

- `roster`: the `standings` and `spectators` fields of `match_state`. When they are left out, the event says
  so with `rosterOmitted: true`, so the client never has to guess from a missing field. The rest of
  `match_state` is still sent every time; its timer changes every tick anyway.
- `weapon:<entityId>`: another player's whole `weapon_state` event. The client's own `weapon_state` is never
  left out, because prediction reconciles against it every snapshot. "Own" is decided on the server by
  `toClientKey(client.entityId)`. A spectator with no entity has no own state, so every `weapon_state` they
  get falls under this rule.

**The rule, per client and per key.** The server keeps the value last sent (a string) and `since`, the first
tick it was sent with that value. For snapshot T:

1. If T is this client's refresh snapshot (every 125th, about every 2 seconds), send the value. If it differs
   from the kept one, keep it with `since = T`.
2. Otherwise, if the value differs from the kept one, send it and keep it with `since = T`.
3. Otherwise it is unchanged: send it while `lastAckedTick < since`, and leave it out once
   `lastAckedTick >= since`.

**Why it holds, and the one thing it needs.** The rule is safe if the client has stored a snapshot's values
whenever it acks that snapshot. If tick A is acked and A ≥ `since`, then either A carried the value, or A left
it out because an earlier snapshot at or after `since` had been acked. Followed back, some acked snapshot
carried the current value. Every snapshot from `since` on carries the same value or nothing. The receiver
never takes a tick older than one it already took, so an older value cannot come back. A dropped, late or
rejected snapshot is never acked, so its values are sent again.

Today the client acks **before** it processes events, and an exception in any handler skips the rest of the
snapshot. So the client change below stores the two kinds of values first, in their own guarded step, before
any other handler runs. The engine's ack order stays as it is. Moving the ack after the game code would stop
all acks while some handler keeps throwing, so every snapshot would go out full: a worse failure than the one
it prevents.

**Client changes.**

- **Store first.** The first step of `Game.onServerStateUpdate`, before spectator cycling and
  `syncFollowedSubject`, does three things. It runs `MatchStateManager.processEvent` for the snapshot's
  `match_state`, and it stores every `weapon_state` in a per-entity cache. It also sets `enemyWeapons` from
  those events. It sits in its own `try`, so nothing else can make it skip a snapshot. The `match_state` and
  the other players' `weapon_state` cases in the event loop then have nothing left to do, so nothing is
  processed twice. `processEvent` only assigns fields and fires phase callbacks on a phase change, each in its
  own `try`.
- `MatchStateManager.processEvent` keeps the previous `standings` and `spectators` only when the event
  carries `rosterOmitted: true`. A missing field without the marker still means empty, as today and as
  `EndgameStandings.test.ts` expects.
- **Spectating.** On a target change, `SpectateView.syncFollowedSubject` runs `handleSpectatedWeaponState`
  with the cached state of the new target: weapon, inventory and ammo. Today the HUD keeps the previous
  target's ammo until the new target's next event. Under this plan that event could be a long time coming,
  so without the cache the numbers shown would be wrong, not just late. Showing the same weapon twice must do
  nothing; a test checks it.
- **Hardening, useful even today.** Each event in the `handleServerStateUpdate` loop gets its own `try`, so
  one failing effect cannot drop the kill feed, damage numbers and the rest of the snapshot.
- Clear the weapon cache and `enemyWeapons` in `Game.shutdown()`, next to the `MatchStateManager` reset that
  is already there. `enemyWeapons` is never cleared today. A resume happens inside the engine with no hook for
  the game, and none is needed: after a resume the server sends everything again, which overwrites the
  caches.

**Server bookkeeping.** Each value is turned into a string once per snapshot, outside the client loop: about
17 strings, not 17 per client. The refresh counts its own snapshots and does not depend on the entity
baseline, so entity deltas, the entity full snapshot every 64th and PVS work exactly as now. Each client keeps
its sent strings and `since` ticks on `ClientInfo`. They are cleared at the same spot as `sentSnapshots` on
resume, and entries for entities that are gone are dropped. The event objects in the shared `GameState` are
never changed, because the demo recorder encodes them after the broadcast. The client's copy gets a new
events array, and a copied `match_state` without the two fields.

## Risks and how each is covered

Each risk below has its own fix, so the refresh is a safety net, not part of the design. If something still
slips, the worst case is a stale scoreboard roster or another player's weapon until the next refresh, at most
about 2 seconds. Over WebSocket every refresh arrives. On a lossy link later, each lost refresh adds about 2
seconds.

| Risk | What could go wrong | Covered by |
| --- | --- | --- |
| Ack sent before events run | A handler throws, the snapshot is acked, its values were never stored | The client stores values first, in their own guarded step; each event handler gets its own `try` |
| Lost or late snapshot | A change rides only in a snapshot that never arrives | Values are sent until a snapshot carrying them is acked; unacked means resent |
| Out-of-order delivery (WebTransport later) | An old value arrives after a new one | `SnapshotReceiver` drops ticks not newer than the last; the server keys on ack ticks, not send order |
| Snapshot dropped for a missing baseline | Its events are lost | It is not acked either, so the server keeps sending |
| Value changes and changes back (A, B, A) | Client holds B; the server sees A again | Each change resets `since`, so A is sent again until acked |
| Resume on a new connection | Server thinks the new socket has old values | Kept values cleared with `sentSnapshots` on resume, so the server sends everything again |
| Switching spectate target | HUD shows the previous target's ammo | Cached state of the new target applied on the switch |
| Free-fly spectator | Every `weapon_state` is someone else's, so all can be left out | Same cache; covered by the convergence test with a spectator client |
| A server that leaves the roster out for real (older build, other tools) | Client keeps a stale roster | Kept only with the explicit `rosterOmitted` marker; otherwise empty, as today |
| Demo recording | Per-client edits leak into the shared state the demo encodes | Shared events are never changed; the client copy gets new objects. A golden test checks a demo frame stays byte-identical |
| Bots | Bot misses data it reads | Bots read only their own `weapon_state` and `match_state` fields that stay in every snapshot |
| Old client, new server | Old client treats a missing roster as empty | Client and server already ship together (the head-hit change requires it). An old client would only lose the post-game standings |
| Ping wired into `standings` later | The roster would change every snapshot and the saving would vanish quietly | Note in the code; the benchmark would show it |
| Server CPU | Comparing values per client costs time | Strings made once per snapshot; per client only a compare. The benchmark must show no rise |

Not changed: the binary layout (the only new thing on the wire is the JSON field `rosterOmitted`), the event
codes, the demo format, the engine, entity and player delta compression, and anything about your own player.

## Stages

Each stage is its own commit with its own tests, and stops for a look before the next.

1. **Safety net first, no behaviour change.**
   - A convergence test. It runs the real `SnapshotBroadcaster` against real `SnapshotReceiver` clients over
     a fake link that drops, delays and reorders snapshots and acks. One client plays, one free-flies as a
     spectator, and one switches spectate targets. After every quiet stretch, each client's view of every
     player's weapon and ammo, and of the roster, must equal the server's. It must pass on today's code before
     anything changes, and keep passing after.
   - A benchmark with play in it, `snapshot.broadcast16.play`: the timer ticks, some players fire every
     snapshot, and a kill happens now and then, with bytes per client reported. Today's number is recorded as
     the baseline.
   - A demo golden test: one recorded frame's bytes.
2. **Client hardening.** Store values first, one `try` per event handler, the spectate cache, and clearing
   the caches in `Game.shutdown()`. It changes nothing on the wire and is worth having even without the rest.
3. **Roster on change.** Server bookkeeping, the `rosterOmitted` marker and the `MatchStateManager` change.
   Expected: about 1,185 bytes saved in every snapshot.
4. **Other players' weapons on change.** Server bookkeeping per entity. Expected: about 2,500 bytes saved
   while players are idle, and much less in a firefight, where `ammo` and `lastFireTick` change on every
   shot.
5. **Measure and write up.** The benchmark before and after, and the v0.9.26 changelog. Then a play-test:
   S&D spectating, free-fly spectating, the scoreboard during play and post-game, and a demo recorded and
   played back.

Tests that will need updating along the way: `SpectatedWeaponHUD`, `SpectateView`, `EndgameStandings`
(widened, not reversed), `DemoServiceLifecycle`, `SnapshotBaseline`, `SnapshotBroadcasterPvs` and
`KnockbackReplay`.

Left for later, each needing its own decision:

- A compact binary `weapon_state` under a new event code. It would take each remaining one from about 168
  bytes to about 40. That is a wire change, so old demos would keep decoding under the old code.
- Encoding the shared events once per snapshot instead of once per client: CPU only.
- Numeric entity ids: a wire and demo format change, worth the least.
