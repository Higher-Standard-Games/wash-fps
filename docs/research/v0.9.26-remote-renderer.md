## The rule

Each stage must leave every remote player looking exactly as before, every frame: position, rotation, crouch
height, animation and its speed, team colour and outline, weapon, quad glow, and whether the body, hitbox and
weapon are drawn. Stage 0 builds a test that records all of that and compares it.

The reasoning below is what each stage rests on. Benchmarks are not a gate: when a number is wanted, a small CLI
script mimics what the client does (Tarmo, 2026-10-07) and is run then.

## What runs today

`render()` is called once per frame. For each remote player that is alive (16 players at 144 fps is 2,304
player-frames a second) it does, in this order:

| Step | Code | Work per player per frame |
| --- | --- | --- |
| Sample | `SnapshotBuffer.sample` (engine) | Two Cvar lookups, a scan of the snapshot buffer to find the bracketing pair, `performance.now()`, and a new result object |
| Hitbox | `render()` `:535` | `cl_remotehitbox` Cvar lookup |
| Style | `applyHitboxVisualStyle` → `getPlayerModelVisualStyleKey` | A 7-element array, 6 Cvar lookups and a `join`, only to find nothing changed |
| Root motion | `PlayerModelManager.resetRootMotion` (engine) | **`getChildTransformNodes(false)` walks the whole skeleton (a Mixamo rig has about 65 joints), builds an array of them, and for each one does `name.split("/").pop().toLowerCase()`: about 65 arrays and 130 strings, to find the same three nodes every time** |
| Enable | `updateModel` `:1336` | `getChildMeshes()` builds an array; the body and every child mesh are switched on |
| Anim debug | `_animDebug` | `cl_animdebug` Cvar lookup |
| PVS | `applyEntityLod` | Two `new Vector3`, three BSP lookups; **a culled player is switched off again, right after being switched on** |

Switching a node on or off is not free in Babylon: `setEnabled` with a new value walks every descendant
(`_syncParentEnabledState`) and fires an observable. So a player behind a wall costs two full skeleton walks a
frame for nothing.

By reading, the root-motion walk is the biggest item: roughly 16 × 144 × 200 ≈ 460,000 short-lived objects a second
at 16 players, against about 10,000 for everything else together. That is an estimate from the code, not a
measurement. The real rig is on Tarmo's desktop, so the test and any benchmark script use a stand-in with the
same nesting and 65 joints.

What is already fine and stays as is: `playAnimation` returns at once when the clip has not changed, the weapon
model is only rebuilt when the weapon changes, `setAnimationActive` only acts on a change, and the quad glow only
runs for a quad carrier.

## Found while planning: a culled player comes back without a weapon

`applyEntityLod` switches the hand weapon off when a player is out of PVS (`:1157`), but nothing switches it
back on when they come into view again. The body comes back because `updateModel` re-enables the anchor every
frame; the weapon is not under the anchor. `attachToBone` parents it to the `Bone`, so it has its own enabled
state, and only `setHiddenEntity` (`:243`) ever turns it back on. A rebuild on the next weapon change hides the
problem until then.

So in game: a player who walks behind a wall and back reappears empty-handed until they switch weapons. Found by
reading; the parity test in stage 0 will show it. It gets its own fix and its own test that fails on today's code,
landed before stage 2, and the parity recording is taken after that fix so the stages are compared against
correct behaviour. Worth a look in Tarmo's next play test: does anyone ever run around without a gun?

## Stages

### 0. Safety net

- **Render-state test** (`client/__tests__/RemotePlayerRenderParity.test.ts`). A `NullEngine` scene, a
  `RemotePlayerRenderer` with a stand-in `PlayerModelManager` whose instances copy vanguard.glb's nesting
  (`__root__ > RootNode > mixamorig:Hips > …`, 65 joints, two skinned child meshes) and a hand weapon attached
  with `attachToBone`, as the game does. Scripted snapshots for 8 players cover running, strafing, crouching,
  sliding, jumping, a teleport, a death and respawn, a weapon change, a team change, quad on and off, a
  hidden (followed) player, and a stand-in PVS culler that hides some players on some frames. After every
  frame the test records, per player: anchor and hitbox position and rotation, hitbox scale, the enabled state
  of hitbox, anchor, body, each child mesh and weapon, `isVisible`, `visibility`,
  `alwaysSelectAsActiveMesh`, current clip, `speedRatio`, whether the animation is playing, the applied style
  key, and the root-motion and hip positions. The recording from today's code is checked in as the expected
  result; every later stage must reproduce it exactly.

When a number is wanted, a CLI script (`bench/remote-render.ts`, run with `vite-node`) drives the same stand-in:
16 players moving, 4 of them culled, many frames, reporting microseconds per frame and young-generation GC runs
(from Node's `gc` performance entries). Written when needed, not as a gate.

### 1. Root-motion nodes found once (engine)

`PlayerModelManager.createInstance` already looks up the hips once (`hipsBind`). It will look up the
root-motion nodes (`rootnode`, `armature`, `__root__`) the same way and keep them on the instance;
`resetRootMotion` resets that list. Instances built without it (tests, old callers) keep today's walk.

Why the result is the same: the skeleton is cloned once per instance and never re-parented. The hand weapon
is attached with `attachToBone`, which parents it to the `Bone`, not into the mesh's node tree, so today's walk
never reached it either (checked in `transformNode.pure.js`; the parity test attaches a weapon to make sure).

### 2. Visibility decided before enabling

Today: switch everything on, then switch culled players off. After: decide first (hidden entity, PVS), then switch
on only what will be drawn, and only when it is not on already. The child-mesh list is taken once per instance,
not built per frame. The final state each frame is the one today's code leaves, which the parity test checks;
a culled player no longer walks its skeleton twice a frame.

Order that must not change: `playAnimation` (in `updateModel`) runs before `setAnimationActive` (in
`applyEntityLod`), because a clip change builds a new animation group that starts playing, and a culled or distant
player's must then be paused in the same frame.

`alwaysSelectAsActiveMesh` (no frustum culling for bodies) stays exactly as it is. Changing that might save more
GPU time than all of this, but it works around bodies vanishing because of stale skinned bounds, and only a play
test can show it is safe. Not part of this plan.

### 3. Per-frame reads hoisted

`cl_remotehitbox` and `cl_animdebug` are read once per frame. The style key is computed once per team slot per
frame (there are three slots) and handed to `applyHitboxVisualStyle`, instead of once per player. The two PVS
probe points use one scratch vector. Same values, fewer reads.

### 4. Sampling without per-player garbage (engine)

`SnapshotBuffer` gets a frame-level call that reads the two Cvars, takes the render time and finds the bracketing
snapshots once per frame, then samples each player into a reusable object. Only `render()` uses it;
`sample()` and `getEntitySample()` keep returning fresh objects, because callers outside the renderer keep them.
`getLatestEntityIds` stops building a new Set each frame.

One visible difference, and it is a fix: today each player is sampled at a slightly different time, because
`performance.now()` is read once per player. After this, every player is sampled at the same instant, as the
server simulated them. The parity test samples at a fixed clock, so it is unaffected; the difference is
microseconds.

Before using a reused object, every place `render()` passes `interp` to was read to check it does not keep it
past the frame: `createHitbox` copies the position into its own `Vector3`, `playTeleportEffect` copies, and
`liquidInteractions.notify` gets a new object literal. That check is part of this stage's review.

## Risks

| Risk | Guard |
| --- | --- |
| A body, weapon or hitbox not drawn when it should be (or drawn when culled) | Parity test records every enabled flag on every frame, including hidden-entity and PVS cases |
| A pose drifting because a root-motion node was missed | Parity test records root-motion and hip positions; stage 1 keeps the old walk when the list is missing |
| A reused sample object kept by someone after the frame | Only `render()` uses it; every consumer read in review; public sampling unchanged |
| A team colour or outline change not picked up | Style key still recomputed every frame, per slot instead of per player; parity test changes team and Cvars mid-run |
| The stand-in rig differs from vanguard.glb | Nesting copied from the existing root-motion test; Tarmo's play test on the real model before merging |

Stages 1 and 4 touch the engine (shag), the rest wash-fps. Merge order as usual: wash-fps first, then shag.
