## The four patterns

1. **Off in one place, on in another.** Something is switched off on one path (PVS, death, hiding, pause), and
   only some paths switch it back on.
2. **State frozen while skipped.** A loop returns early for some case, its per-frame state goes stale, and the
   first frame after acts on the stale value.
3. **Twin cleanup paths that drifted.** Several paths reset the same thing, and a fix landed in only one.
4. **Async loads, timers and leftovers.** A load or timer leaves debris, or lands after its owner is gone.

"Other" marks a bug found on the way that fits none of them.

## How sure we are

Every finding was traced through the code by reading, including callers, and Babylon behaviour was checked in
Babylon's own source (`node_modules/@babylonjs/core`), not from memory. None has been reproduced in a running
game yet: the maps and models are on Tarmo's desktop. **Confirmed** means the whole path was read; **probable**
means one step was inferred. Findings marked ✔ were re-checked a second time against the code before writing
this up.

## Checked and fine

Each sweep also listed what looked like a bug and is handled. In short: late async loads are dropped by
generation checks in the post-game showcase, demo view model, dropped weapons and remote weapons; seek-landing
events are suppressed; corpses are never re-created from the snapshot buffer; effect renderers (muzzle, rail,

## What this says about the code

The server and the netcode came out well. Every high finding is in the client's presentation layer, and they
share causes that a few shared rules would prevent:

- **One way to hide and show a body**, used by PVS, spectate, death and ragdolls alike (W1, W2, R1, R4, E2).
- **One disposal helper per kind of thing** (player model, loaded weapon model, effect), used by every path that
  removes one (R3, R5, W4, E5, E9).
- **One session reset** that every per-session system registers with, called from `shutdown()` and map unload
  (S2, S3, L6, E8, D4, D10).
- **State on the event context is a getter/setter**, never a copy (L1).

These shape the fix plan; they are not changes yet.

## Fix plan

### How every fix lands

- **One test per fix that fails on today's code**, run against the old code before the fix goes in, as with the
  snapshot work. Most of these are headless: `NullEngine` scenes, a fake snapshot stream, fake timers.
- **Batches are small and land one at a time**, each with the full suite, typecheck, lint, a build that boots to
  the menu, and this table updated. wash-fps first, then shag repinned, as always.
- **Shared causes get a shared fix**, so a bug fixed once stays fixed on every path (batches 3, 5 and 6).
- **What only a play test can confirm is listed per batch**, and the batch notes say what changes on screen.

### Batch 1: L3 and L1 (small, and needed before the snapshot work merges)

**L3, your gun while watching a teammate.** In `handleWeaponStateSync`, while `ctx.spectatingEntityId` is set,
skip the HUD update and the view-model reconcile; keep the inventory, reload and prediction sync, which must
stay current. When the spectate ends, the next snapshot's reconcile puts your own gun back: it is level-triggered
against the displayed weapon (`GameEvents.ts:978-1001`) and runs on every snapshot, because your own weapon state
is always sent. A switch to a new teammate already shows their stored weapon (snapshot work, stage 2).
Test: dead, watching a teammate, several snapshots carrying only your own weapon state; the HUD and view model
keep the teammate's weapon. Fails today.

**L1, always the blade.** Make `_lastServerWeapon` and `_localCharging` getter/setter pairs on the event context,
like `_isPlayerDead`, so Game and the event layer share one value. Reset both in `shutdown()`, or a reconnect
would start with the last session's weapon. Test: after a weapon state for the rocket launcher,
`getCurrentWeaponId()` is `"rlauncher"`. Fails today.

**What changes on screen with L1, which you have never seen working:** per-weapon crosshairs, the red-X
out-of-ammo crosshair, the empty click, and the rocket, plasma and grenade launchers raising to the sights when
fired from the hip, which also sends the server the alt-fire those weapons expect (`FPSController.ts:742-745`). That last one changes how those weapons feel, so it needs your
play test before merging.

### Batch 2: the S&D camera (S1, S4)

**S1.** Track the death edge (`_wasDeadLastFrame`, `_deathAtMs`) every frame, from `syncFollowedSubject`, which
`Game` calls every frame (`Game.ts:1347`), instead of only from the death camera. **S4.** In the same per-frame
step, stop the teammate view when you are alive (`_spectatingEntityId` is only ever the teammate view; a true
spectator's chase target lives elsewhere, so this cannot touch it). Tests: two deaths in one session, each gets
the corpse camera first; a revive with no "dead, not Active" frame in between ends the teammate view.

**Decided (Tarmo, 2026-10-08):** living players do **not** get the round-end camera; they stay where they are, hear
the blast (it is already a 2D sound for everyone, `BombSiteMarkers.ts:296-299`) and see it if they are near the
site (the effect is spawned on every client). Dead players get the static camera on the bomb. That is what the code
does today; only the misleading comment in `updateRoundEndCamera` gets corrected.

**New feature, not a bug (Tarmo, 2026-10-08):** the bomb blasts should damage players near the site, enough to gib
them, with no score penalty (unlike a self-frag). Today the detonation is effects only: the server builds the
explosion points (`SearchAndDestroy.ts:623`) and deals no damage. Planned separately once the batches are in: damage
from each blast point, as a world kill credited to no one, with no death or suicide counted against the victim,
during the round-end phase so it cannot change who won.

### Batch 3: PVS comings and goings (W2, W1, R1, E2/R4, W6)

The shared rule: leaving PVS is not being removed.

- **W2, projectiles.** Keep a projectile's type when it leaves PVS, and drop entries by age instead: older than the
  longest projectile lifetime (rockets, 10 s) plus a second. `projectile_impact` carries no entity id, so age is
  the only signal. The projectile then reappears where it is, with its model and trail.
- **W1, dropped weapons.** Recommended: the server stops PVS-filtering dropped weapons. They are few and lie
  still, so after the first snapshot delta compression makes them almost free, and the client then knows that
  "missing" means "gone". The alternative, hiding on absence and guessing when to dispose, is a heuristic
  that is wrong on every pickup made out of view. This is a small netcode change, so it gets its own test in the
  broadcaster and the convergence test is re-run.
- **W1 in detail (asked for by Tarmo, 2026-10-08).** How a dropped weapon reaches the screen today:
  1. A death or swap drops a weapon. The server sends a one-off `weapon_drop` event with the toss velocity, and
     from then on an `item_` entity with a position, for 15 s or until someone picks it up
     (`DroppedWeaponSystem.ts:68`). The server runs a simple toss until the weapon settles, then it lies still.
  2. Every snapshot, each client's copy is filtered by the server PVS (`SnapshotBroadcaster.filterStateForClient`):
     an entity with a position is sent only if its cluster is visible from the client's.
  3. The client keeps a visual (model, glow, Havok body) per `item_` id. A new id gets a visual that is tossed with
     the event's velocity; an id that is missing from a snapshot is disposed (`DroppedWeaponRenderer.ts:405-425`).

  So "out of view" and "picked up" look the same to the client. Walk out of the room and the weapon is disposed;
  walk back in and it is built from scratch: model loaded again, a new physics body with a random spin, landing at
  a new angle (W1), and the loader leaves debris each time (W4).

  **The proposed change.** The server sends `item_` entities to everyone, whatever the PVS. The client then disposes
  a visual only when the server really removed it, and hides one that is out of view with the client's own PVS
  culler, the same check remote players already use (`RemotePlayerRenderer.applyEntityLod`). Hidden is
  `setEnabled(false)`: no draw call, the physics body stays asleep, nothing reloads.

  **What it costs.**
  - *Wire.* A settled weapon does not change, so after the client has it in its baseline delta compression sends
    nothing for it, except in the full snapshot every 64th. A falling weapon costs a position per snapshot for about
    a second. With a 15 s lifetime, even a busy 16-player match has a handful to a few dozen on the map.
  - *Rendering.* Unchanged for what is on screen. Weapons behind walls are hidden by the client culler, as remote
    players are; without it they would at most be frustum-tested small meshes.
  - *Information.* A modified client could see where weapons lie behind walls. Weapon spawn timers are already
    global (`pickupActiveMask`), and a dropped weapon says less than a player position, which stays PVS-filtered.

  **Why not fix it on the client alone.** The client would have to hide a missing weapon and guess when it is
  really gone. Any timeout is wrong for every weapon picked up out of view: it lingers until the timeout, then
  vanishes in front of you. Only the server knows.

  **What stays the same.** Players and projectiles stay PVS-filtered. The snapshot work's leave-out rule is
  untouched: it covers events, and `item_` entities are entities. Test: a broadcaster test with PVS on, where a
  culled client still gets the `item_` entity and not a culled player; a renderer test where an id that drops out
  of view is hidden and kept, then shown again without a rebuild.
- **R1, the hand weapon.** Switch the weapon on wherever the body is switched on; PVS switches both off.
- **E2/R4, invisible corpses.** `detachModel` switches the anchor and weapon on before handing the model to the
  ragdoll. For the player you watch in first person the death camera owns the view, so their corpse is drawn
  from outside their eyes; a test checks the camera is not inside it.
- **W6, tab return.** Clear the drawn-projectile set along with the visuals.
