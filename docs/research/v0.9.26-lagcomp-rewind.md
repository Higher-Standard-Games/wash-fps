## How a shot is judged today

1. The client stamps every command with the newest snapshot tick it has received (`viewTick`).
2. The server queues the command (`inputQueue`, at most `MAX_INPUT_BUFFER` = 6) and simulates one per tick.
3. When the command fires, `WeaponSystem.rewindFor` rewinds other players to `viewTick - interpTicks`, where
   `interpTicks` is the server's guess at how far behind the newest snapshot the client draws (one snapshot
   interval, 2 ticks at 60 Hz snapshots).
4. `LagCompensation.rewindToTick` clamps that to 100 ms (`lagcomp/config.ts`).

Nothing compares the claimed `viewTick` with anything the server measures. So a client with 3 ms of ping can stamp
its commands 100 ms old and be judged against where targets were 100 ms ago, which is the "backtrack" cheat. The
server does measure the round trip itself: `client.ping`, the time from sending a snapshot to receiving its ack,
smoothed (`GameServer.recordAckRoundTrip`). A client cannot shorten it, only lengthen it.

## What an honest claim looks like (measured)

A real `GameServer` and a client that behaves like the game's, over a real socket with latency held in both
directions (the `LagCompensationLatency` harness): it acks every snapshot, stamps the newest snapshot tick, and
sends one command per 8 ms tick, as `FPSController`'s accumulator does. Jitter keeps frames in order, as a
WebSocket does. 300 commands per profile; "age" is how old the claimed view is when the server simulates the
command; "age − ping" is what a check against ping has to allow.

| One way | Jitter | Ping | Age p50 / p99 | Age − ping p50 / p95 / p99 / max |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0 | 3 | 16 / 24 | 13 / 21 / 22 / 22 |
| 10 | 0 | 21 | 40 / 48 | 19 / 28 / 28 / 28 |
| 25 | 0 | 51 | 64 / 72 | 14 / 22 / 22 / 22 |
| 50 | 0 | 101 | 120 / 128 | 19 / 27 / 28 / 28 |
| 10 | 0–20 | 46 | 64 / 72 | 19 / 28 / 32 / 33 |
| 25 | 0–30 | 89 | 104 / 120 | 19 / 31 / 36 / 36 |
| 50 | 0–40 | 159 | 176 / 192 | 18 / 33 / 45 / 45 |

All values in ms. What it says:

- An honest claim is about ping plus 15–20 ms (a snapshot interval and the wait for the next tick), and with
  jitter up to about 45 ms more than ping.
- **The input queue matters more than ping when it fills.** A first run sent commands every 7 ms instead of 8: the
  queue sat at 6 and every claim was 45–60 ms older than ping, even at 0 latency. A real client fills the queue
  the same way after a frame hitch (`FPSController` catches up to 100 ms of commands at once). The server knows
  when each command arrived, so the check must measure the claim at **arrival**, not when the command is
  simulated. Otherwise a hitch would clamp an honest player.
- From about 45 ms one way the honest claim is already over 100 ms, so those players are clamped by today's cap
  and a ping check changes nothing for them.

These numbers are from one machine and a simulated link. Stage 0 collects the same thing from real matches before
anything is enforced.

## Stages

Each stage is its own commit with tests that fail on the code before it. Nothing changes what an honest player
gets until stage 2 is switched from "log" to "clamp", and that switch is one constant.

### 0. Measure in matches (log only)

The server records, per command, the claim at arrival (`arrivalTick − viewTick`) and the client's ping at that
moment, and adds a percentile summary of "claim − ping" per player to the existing `[Telemetry]` line. No gameplay
change. Tarmo's play test, a few matches on real connections (Wi-Fi, mobile, a distant server), gives the margin.

### 1. View tick never goes backwards

An honest client stamps the newest snapshot it has, and snapshots arrive in order, so its `viewTick` never goes
down. The backtrack cheat does exactly that: normal stamps while moving, an old one on the shot. Rule: a command's
`viewTick` is raised to the highest one this connection has sent. Reset on a new connection and on resume (the
client starts counting again). Redundant copies of old commands are already dropped by the sequence check, so
they never reach this.

No tuning, nothing for honest players to lose. It does not stop a client that stamps everything consistently
old; stage 2 does.

Tests: a protocol client at 0, 25 and 50 ms with jitter is never adjusted; a client that drops its stamp only
on the firing command is judged at its previous stamp; a resumed session starts fresh.

### 2. Rewind limited by measured ping

At arrival, allowed claim = ping + one snapshot interval + margin, and never more than 100 ms. A claim older than
that is raised to the allowed age, so the shot still counts, just judged a little later. It is never rejected.

- **Margin:** 45 ms from the measurements above (their worst case), to be confirmed by stage 0. That still takes
  a 3 ms-ping cheater from 100 ms of rewind down to about 65 ms; with stage 1, they can no longer choose which
  shots get it.
- **Before the first ack is timed** (`ping` = 0), there is no limit beyond today's cap, so a fresh joiner is never
  clamped on a missing number.
- **Spikes:** the ping is smoothed (a quarter of each new sample, about 60 samples a second), so it follows a real
  spike within about 100 ms. During that window a shot is judged slightly later, not dropped.
- **Mode switch** in `lagcomp/config.ts`: `off`, `log` (count what would be clamped, in `[Telemetry]`), `clamp`.
  Lands as `log`; `clamp` after a play test shows honest players are not touched.

Tests: honest profiles from the table are never clamped (in `clamp` mode); a 0-ping client stamping 100 ms old is
judged at about ping + margin; a full input queue does not count against the claim; `off` behaves exactly as today.

What it does not stop, written down so nobody thinks it does: a client that delays its acks on purpose raises its
own measured ping and gets up to 100 ms, as today. That costs the cheater a real-looking lag in everything else the
server times; the 100 ms cap remains the limit there.

### 3. Render timing (found while planning, fixed)

**First reading, wrong:** the plan said the client draws 50 ms behind while the server assumes 16 ms. 50 ms is only
the starting value; `SnapshotBuffer.updateInterpDelay` brings it down to about 17 ms within a few snapshots on a
steady link, which matches the server's assumption.

**What was actually wrong, measured.** Once clock sync is up, the game hands the buffer each snapshot's server
timestamp (`GameEvents.ts:620`), and the buffer timed snapshots by it: when the server sent them. It still drew at
`now − interpDelay`, so it drew about 17 ms behind the server's present at any ping, which is ahead of anything that
has arrived. Every remote body was extrapolated, by up to 60 ms (`MAX_EXTRAPOLATION_SEC`), and past that froze. The
server judges a shot at the newest snapshot tick less 2, so it judged shots a network trip earlier than what the
shooter saw.

Measured with the real `ClockSync` and `SnapshotBuffer` against a real `GameServer` (ticks are 8 ms; "judged −
drawn" is where the server rewinds to minus what the shooter saw, negative meaning older):

| One way | Jitter | Before: judged − drawn (p50) | After | Without clock sync |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0 | −1.1 | −1.0 | −0.9 |
| 25 | 0 | −4.0 | −0.9 | −0.8 |
| 50 | 0 | −7.2 | −0.9 | −0.8 |
| 100 | 0 | | −0.9 | −0.8 |
| 25 | 0–30 | −4.7 | −1.3 | +0.3 |
| 50 | 0–40 | | −1.8 | +0.3 |

At 50 ms one way that was 58 ms, about 18 units for a strafing player: over half a body width.

**Fix (engine, `SnapshotBuffer.getSnapTime`).** A server-timestamped snapshot counts as arriving at its timestamp
plus the network's transit time, the fastest of the last 20 snapshots (arrival minus timestamp). Snapshots keep the
server's even spacing, free of arrival jitter, and the buffer draws `interpDelay` behind the newest one that has
actually arrived, as it does without clock sync. An error in the clock offset cancels out, because the transit is
measured with the same offset. Tests: `SnapshotBuffer.test.ts` (+2: draws behind the newest arrival at 0, 50 and
100 ms transit; same result with the offset 200 ms off either way), `RemoteRenderTiming.test.ts` (end to end at
50 ms each way: within 2 ticks, and drawn behind the newest snapshot). Both fail on the old code (7.1 ticks off).

**What players will notice:** other players and server projectiles are drawn a network trip later than before, but
smoothly interpolated instead of guessed ahead, and shots at moving players land where the shooter saw them. On a
high ping, bodies no longer stall at the 60 ms extrapolation limit.

Left as is: the server still assumes the client draws 2 ticks behind. Under heavy jitter the client's delay grows
(to about 30 ms at 40 ms of jitter), leaving shots judged up to 2 ticks old. Sending the drawn tick would close that,
bounded by stage 2's check; it is not needed for this fix.

## Risks

| Risk | Guard |
| --- | --- |
| Honest players lose hits on jittery links | Clamp, never reject; margin from real matches; `log` before `clamp` |
| A frame hitch fills the input queue and looks like a stale claim | Claim measured at arrival, not at simulation |
| A missing or stale ping clamps a new joiner | No ping yet means today's behaviour |
| View tick resets on reconnect look like going backwards | Stage 1 resets per connection and on resume |
| The check costs server time | One subtraction and a compare per command |
