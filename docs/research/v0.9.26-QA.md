# v0.9.26 QA: second list (no media needed)

The v0.9.25 list ([v0.9.25-QA.md](./v0.9.25-QA.md)) is done or closed, apart from work that needs a play-test or match data. This second list covers only what can be checked without the game's maps and media: unit tests, the deterministic re-simulation (`server/ReSim.ts`), and the benchmarks in `bench/`.

## How this was produced

- **Method:** read `WeaponSystem.ts`, `GameServer.ts`, `MovementValidator.ts`, `AuthorityGuards.ts` and the per-frame path of `RemotePlayerRenderer.ts`; measured snapshot bytes with a new benchmark (`snapshot.broadcast16`).
- **Evidence levels:**
  - **Reproduced:** a scratch test drove the real code and showed the failure.
  - **Traced:** followed line by line in the code, not run.
  - **Unverified:** plausible, not yet traced.
- **Play-test:** none was possible. Two of the bugs below change what a player sees, so confirm them in a match too.

## B1: Pickup auto-switch is undone

**Finding.** `addWeapon` sets `currentWeapon` and clears the slot edge-detector with `lastWeaponSlot.delete(entityId)` (`WeaponSystem.ts:608`, `:621`, `:643`, `:685`).

The server's `input.weaponSlot` is sticky: movement only writes values above 0 (`FPSMovementSubsystem.ts:756`), and respawn sets it to 1 (`GametypeController.ts:838`). So on the next `update` the detector sees the previous slot as 0 and the current one as 1. It treats that as a press and equips slot 1 again (`:856`). `addWeapon` also never sets `lastSwitchTick`, so the switch delay does not stop it.

**Reproduced:** spawn with the blade, pick up the machinegun, and `currentWeapon` over the next ticks is `machinegun, blade, blade, blade`. `WeaponAutoSwitch.test.ts` never runs `update()` after `addWeapon`, so it misses this.

**Fix.** Set `lastWeaponSlot` to the entity's current `input.weaponSlot` instead of deleting it. That is the "no change" state, so only a new press switches. A test runs `update()` after the pickup.

## B2: Uncharged full-damage blade charge

**Finding.** `equip()` resets `chargeStartTick` (`:471`) but not `wasAltFireDown`. The standard-weapon branch keeps `wasAltFireDown` true while alt-fire is held (`:1068`).

So: hold alt-fire on the machinegun, switch to the blade, release. The release branch (`:977`) computes `heldTicks = tickNum - 0`, clamps it to the maximum, and fires `chargedDamageMax`. No charge-start event is ever sent, so other players get no warning.

**Reproduced:** 50 damage (`chargedDamageMax`) fired the tick after the switch. Also: `lastAltFireTick` is written (`:991`) and never read, so charged shots have no fire-interval check.

**Fix.** `equip()` clears `wasAltFireDown` and `wasFireButtonDown`, and the release branch requires `chargeStartTick > 0`. Whether charged shots need a minimum interval is a balance call; the default is to leave it as is.

## B3: Snapshot bytes

**Measured** with `snapshot.broadcast16`: 16 clients, the default round loadout, every snapshot acknowledged, no PVS culling.

| Part of one client's delta snapshot | Bytes |
|---|---:|
| `weapon_state`, 16 players (JSON `weapons` and `ammo`, every snapshot) | 2,695 |
| `match_state` (JSON, standings with every name, every snapshot) | 1,513 |
| Entities (46), of which entity id strings | 895 (497) |
| `combat_state`, 16 players | 263 |
| Players (scoreboard rows, delta) | 183 |
| **Total** | **5,809** |

At 62.5 snapshots a second that is about **2.9 Mbit/s to each client and 46 Mbit/s out of a 16-player server**. Broadcasting costs 1,347 µs per snapshot, about 8% of a core. The two JSON events are stringified once per client because encoding is per client.

This corrects the v0.9.25 figure of 1,774 bytes and about 2.5% of a core: that fixture had no clients and no weapons, so it carried neither event.

PVS culling only removes entities, which are 15% of the bytes. On a real map, the two events are an even larger share.

**Design options**, which can be combined:

1. **Send `match_state` only when it changes**, and in full every N snapshots and to a client that just joined. One `JSON.stringify` per snapshot detects the change; most of the time only `timeRemaining` changes, about once a second. The client already keeps its last match state when none arrives (`MatchStateManager.processEvent` only runs on an event).
2. **Send other players' `weapon_state` only when it changes.** Your own stays in every snapshot, because local weapon prediction reconciles against it (`handleWeaponStateSync`). Other players' only drives the third-person model and the spectated HUD. Risk: a demo seek into the middle of a recording needs the last known state. Demos are recorded from the shared snapshot, so periodic full refreshes (option 1's N) cover it.
3. **Encode the shared events once per snapshot** instead of once per client. This changes CPU only, not one byte on the wire. It is an engine change: an encode entry point taking pre-encoded event bytes.
4. **Numeric entity ids** instead of `player_12` strings: 497 bytes of 895. This changes the wire format and the demo format, and is the least worth doing.

Options 1 and 2 together are estimated to bring a steady-state snapshot from 5.8 KB to about 1.5 KB. That is an estimate; the benchmark will say. **Needs a decision** before work starts, because demos and older clients are affected.

## B4: Tick loop spins on a persistent error

`scheduleNextTick` (`GameServer.ts:696`) advances `nextTickAt` only after a successful `tick()`. When `tick()` throws, the catch logs it (rate-limited) and `finally` reschedules with `delay = max(0, nextTickAt - now)`, which is 0 because the deadline is still in the past.

A tick that throws every time therefore runs back to back at `setTimeout(0)` speed. That is one core at 100%, and, if the throw comes after the simulation stepped, the game runs several times faster than real time. `TickLoopResilience.test.ts` only throws from the diagnostic that runs after the loop.

**Fix:** advance `nextTickAt` in the catch (skip the failed tick) and test with fake timers.

## B5: Unbounded client strings

- **Player name:** no length limit or sanitising when there is no admission grant (`GameServer.ts:1338`). It is re-sent to every client in every snapshot's standings and spectator list (`SnapshotBuilder.ts:409–431`), so a 10 KB name costs every player 10 KB × 62.5 a second.
- **Chat:** `handleChat` runs a per-character loop over the whole raw text before the length cap and the rate limit (`:1236–1242`).
- **No `maxPayload`** on the engine's WebSocket server (`WebSocketTransport.ts:112`). Whether `readString` caps its length is unverified.

**Fix:** cap and sanitise names the way chat is sanitised; cap the raw chat length first; set `maxPayload` in the engine.

## B6: Pickup inherits a reload

The pickup paths assign `currentWeapon` directly (`:608`, `:620`, `:641`, `:687`) instead of going through `equip()`, so `reloading` and `reloadEndTick` carry over.

A machinegun mid-reload, then a riotgun pickup: the riotgun cannot fire until the machinegun's reload would have ended (`:917`). `finishReload` (`:885`) then refills the riotgun's clip, and the machinegun's reload is lost.

**Fix:** route the auto-switch through the same reset `equip()` does. A test can confirm it before the fix.

## B7: Lag compensation trusts `viewTick`

The rewind comes only from the client-supplied `viewTick` (`WeaponSystem.ts:386`). It is clamped to 100 ms (`lagcomp/config.ts`) but never compared with the ping the server measures (`GameServer.ts:410`), so a 0-ping client can claim 100 ms of rewind.

Clamping to measured round trip plus a margin is the usual answer. The margin is a design decision, because jitter makes a tight clamp punish honest players.

## B8–B10: smaller items

- **B8, auto-shutdown timer:** `this.shutdownTimer` is reassigned without clearing the old one (`:1062`). Every disconnect while no human is left (bots leaving after post-game) orphans the previous timer. An orphaned timer's callback checks connected clients only, not suspended seats (`:1064`), so it can stop a server that holds a resumable seat. Fix: clear before setting, and count suspended humans in the callback. Fake-timer test.
- **B9, growing maps:**
  - `weaponStates`, `lastSwitchTick` and `lastWeaponSlot` are never cleared when an entity goes, and every rejoin gets a new entity id (`GameServer.ts:1593`). `resetForMatch` clears only the accuracy maps.
  - `lagCompensation.clientLatencies` gets an entry per Join that is never pruned.
  - Ping messages have no rate limit (`:1184`).
- **B10, `MovementValidator`:**
  - The header, the method doc and `GameServer.ts:1614` say over-budget input is dropped; it only adds a strike. The real speed-hack defence is one command per tick and `MAX_INPUT_BUFFER = 6`.
  - Strikes reset on every spectate, rejoin and resume.
  - Untested: budget refill, the 500 ms cap, `onTick`, the unknown-client pass, and the order in `GameServer` (sequence de-dup, validator, sanitise).
  - Fix the docs, add the tests, and decide whether strikes should follow the player rather than the connection.

## B11: Splitting the two largest server files

Natural seams, with the tests that cover them:

- **`WeaponSystem.ts`**
  - Inventory and ammo, about 400 lines (`:415–832`, owns `weaponStates`). Tests: `WeaponSystem`, `WeaponAutoSwitch`, `WeaponDryFire`, `WeaponDropPosition`, `PickupSystem`.
  - The trigger state machine, about 250 lines (`:833–1080`).
  - Hitscan resolution, about 410 lines (`:1366–1775`, owns lag compensation and accuracy). Tests: `HitLocation`, `LagCompensationLatency`, `ElectricalDischarge`, and the `hitscan.resolve16` benchmark.
  - Melee, charged, projectile and water, about 340 lines.
- **`GameServer.ts`**
  - Tick loop and diagnostics, about 320 lines. Tests: `TickLoopResilience`, `GameServerTickRate`, `FixedTickRate`.
  - Session lifecycle, about 430 lines: connect, disconnect, join, resume, spectate, queue. Tests: `SessionResume`, `MatchAdmissionGate`, `SndJoinGate`, `SuspendedSessions`. No test covers the challengers queue, spectate, `RequestSpawn` or `shutdownOnEmpty`.
  - The message router, about 280 lines. Tests: `GameServerProtocolSmoke`, `AmphiProtocol`.
  - Demo recording.

The re-simulation covers only a machinegun loadout with no collision world and no lag compensation (`ReSim.ts:157–178`). So it would not catch a mistake in the blade, charged, pellet, chain, splash or pickup code. Widening its loadout comes first; otherwise this split carries more risk than the `Game.ts` one did.

## B12: Remote player renderer, per frame

Per remote player per frame:

- `snapshotBuffer.sample` returns a new object and does two Cvar lookups.
- `getChildMeshes()` builds an array, and every child is re-enabled, so PVS-culled players are enabled and disabled again each frame.
- `applyHitboxVisualStyle` builds a style key from a 7-element array, 6 Cvar reads and a `join`.
- `cl_remotehitbox` and `cl_animdebug` are read per player; they could be read once per frame.
